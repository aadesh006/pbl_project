Inspection pipeline

STAGE 2
Sandbox exec

STAGE 4
Verdict
Blocked calls are stopped at the hook, not just logged — the package never completes the call.
02

Why an LSM hook, not ptrace or seccomp

There are three common places to intercept a process's syscalls. Each trades off differently between visibility, overhead, and whether you can actually stop the call before it completes.

Approach Where it runs Can block inline Overhead
ptrace Userspace, syscall-by-syscall trap Slow — stop/resume per call High (context switch per syscall)
seccomp-bpf Kernel, filter at syscall entry Yes, but coarse-grained Low, but no argument-level nuance
eBPF/LSM (this project) Kernel, security hook at socket_connect Yes — argument-aware (dest IP) Low — 3.2µs measured

Detection latency

log scale — kernel hook vs. userspace scanning

The 3.2µs figure is a measured value from bpf_ktime_get_ns() on the socket_connect hook itself — the cost of the kernel-side check, not an end-to-end benchmark. The audit and manual-review rows are order-of-magnitude reference points for how those approaches typically operate, not numbers measured against this tool — the axis is log-scaled because the gap between them spans roughly eight orders of magnitude.

05

Core components

Socket-connect hook
A working lsm/socket_connect eBPF program backed by an IP blocklist map — outbound connections to known-bad addresses are refused at the kernel boundary.
Namespace scoping
Filtering keyed off task->nsproxy->pid_ns_for_children so the trace only covers the sandboxed package's own PID namespace, not the host.
Latency measurement
Hook overhead measured with bpf_ktime_get_ns() rather than estimated — the 3.2µs figure above is a real number, not a placeholder.
BPF ↔ C++ event bridge
event_t struct alignment corrected between the BPF side and the C++ userspace side so trace events decode cleanly across the boundary.
hooks/socket_connect.bpf.cSEC("lsm/socket_connect")
SEC("lsm/socket_connect") int BPF_PROG(restrict_connect, struct socket *sock, struct sockaddr *address, int addrlen) { // scope the check to this package's sandbox namespace struct pid_namespace *ns = get_task_ns(bpf_get_current_task_btf()); if (ns != sandbox_ns) return 0; __u64 t0 = bpf_ktime_get_ns(); if (ip_in_blocklist(address)) { emit_event(EVENT_BLOCKED, address, bpf_ktime_get_ns() - t0); return -EPERM; // refused inline, before connect() returns } return 0; }

Against real incidents: Axios & TanStack

Two of 2026's largest npm supply-chain compromises both relied on the exact moment this project sandboxes: an install-time lifecycle script running with full host trust. Neither was caught by static scanning before it shipped — here's what each did, and what part of Shadow Analyzer's design maps to it.

incident.log — axios@1.14.1 / 0.30.4, 2026-03-31 RAT DROPPER
01// maintainer npm token compromised; two versions published directly, bypassing CI/OIDC
02dep phantom dependency plain-crypto-js@4.2.1 added — never imported anywhere in axios source
03postinstall setup.js runs on install, contacts C2 (sfrclak.com:8000)
04payload cross-platform RAT dropped, then setup.js deletes itself and restores a clean package.json
05detected in the wild ~6 min after publish by an external scanner — after infections had already begun
incident.log — @tanstack/* × 42, 2026-05-11 CI WORM
01// GitHub Actions cache poisoned via a pull_request_target Pwn Request; OIDC tokens read from runner /proc/<pid>/mem
02publish 84 malicious versions across 42 @tanstack/* packages, carrying valid SLSA provenance
03install payload downloads the Bun runtime as a living-off-the-land binary
04exec obfuscated payload harvests CI tokens & cloud credentials, self-propagates using stolen tokens
05contained within ~5 hours, but had already spread to 170+ packages by then

Where the sandbox would have intervened

Attack step (both incidents) What caught it in reality Shadow Analyzer's angle
Lifecycle script (postinstall) runs with full host access Nothing — npm runs it by design Namespace-scoped sandbox: the script never touches the real host in the first place
Script opens an outbound connection (C2, or token exfil) Static scanners don't observe runtime network calls socket_connect hook sees and logs every connect() at install time, blocklist match or not
Malware self-deletes / restores clean files post-execution (axios) File-based scans after the fact find nothing Event captured at kernel connect-time — survives userspace cleanup entirely
Payload uses a brand-new C2 domain, not yet on any blocklist Signature/reputation lookups miss unlisted infrastructure Honest gap — today's static IP blocklist wouldn't auto-block it either

The real gain isn't "the blocklist would have had the right IP" — it's that a sandboxed install script attempting any outbound connection at all is itself the anomaly worth surfacing, which is what the threat-intel feed integration and per-package risk scoring on the roadmap below are for: turning "an install script just called home" into an automatic block, not just a log line.
